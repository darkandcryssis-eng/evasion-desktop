# Задание: движок Evasion

Документ прислан владельцем проекта и является полным заданием. Хранится в
репозитории, чтобы каждая сессия начиналась с него, а не с пересказа.
Изменять его нельзя: правки вносит только владелец.

Ты пишешь движок обхода DPI для Windows на Go. Документ — полное задание.

Реализация идёт двумя этапами (1.5.1): этап 0 — режим прокси
в пользовательском пространстве, этап 1 — режим перехвата через WinDivert.
Пакеты `strategy`, `scoring`, `generator`, `control` при переходе между
этапами не меняются.

---

## 1. Цель и границы

### 1.1 Цель

Движок удерживает доступ к заданным группам доменов в рабочем состоянии:
автоматически **порождает**, оценивает и ротирует стратегии обхода DPI,
без участия человека — включая случай, когда работавшая стратегия
перестала работать.

Последний придаток принципиален. Без него задача читается как «настроить
обход», и тогда весь автопилот становится лишней сложностью. Решаемая
проблема — именно деградация стратегий во времени.

### 1.2 В области

- Перехват и модификация трафика: сокеты (этап 0), пакеты (этап 1)
- Собственная реализация десинка: разбор IP/TCP/UDP, разбор TLS
  ClientHello, примитивы манипуляции
- Выбор стратегии **на каждое соединение**, в момент ClientHello
- Автоматический вывод новых стратегий (генетический поиск)
- Непрерывная оценка и ротация на основе **живого трафика**
- Машинно-читаемая поверхность управления: CLI с `--json`

### 1.3 Вне области

- Прокси и туннели как средство обхода (VLESS, WireGuard, Xray): трафик
  не уходит на внешние серверы, IP не меняется, маршрутизация не меняется.
  SOCKS-прокси этапа 0 — локальный инструмент применения десинка,
  а не туннель.
- **Визуальный интерфейс** — реализуется владельцем проекта отдельно (2.2)
- Раздача доступа другим людям, мультиюзер, авторизация, подписки
- Запуск на роутере
- Собственный kernel-драйвер

### 1.4 Жёсткие ограничения

1. **Свой код и свои параметры.** Код существующих инструментов обхода
   и их подобранные наборы параметров (конкретные TTL, байты фейков,
   выигрышные комбинации флагов) не используются.

2. **Механика общего назначения берётся из академических источников**
   с указанием авторства. Базис примитивов — из Geneva (CCS 2019):
   `drop`, `tamper` (правка полей заголовка), `duplicate`, `fragment`.
   Набор намеренно минимален и не содержит знания о конкретном цензоре.
   Направленный поиск по расхождениям TCP-автоматов (SYMTCP, NDSS 2020)
   держится в виду как развитие; в первой версии не реализуется —
   требует символьного исполнения TCP-стека.

3. **WinDivert принимается как данность** (этап 1). Собственный
   WFP-драйвер требует EV-сертификата и подписи — вне области.
   Абстракция перехвата закладывается (п. 7).

4. **Стратегия выбирается на соединение.** Архитектурообразующее
   требование. Следствия:
   - обучение идёт на реальном трафике, а не только на пробах;
   - разные стратегии действуют одновременно для разных соединений,
     что даёт живой A/B;
   - смена стратегии не рвёт существующие соединения;
   - телеметрия собирается в разрезе «стратегия × SNI × время».

5. **Стратегия представляется деревом примитивов, а не строкой флагов.**
   Генератор должен порождать и мутировать структуру. Строка аргументов
   закрыла бы эту возможность.

6. **Генетический поиск работает только в песочнице.** Мутирующий
   алгоритм не допускается к основному трафику. Кандидаты проверяются
   на выделенных соединениях и попадают в рабочий портфель только после
   прохождения статистического порога (5.5). Стратегия, прошедшая
   несколько проверок, может быть везением — без порогов портфель
   наполнится фантомами.

7. **Абстракция перехвата закладывается, вторая реализация не пишется.**
   Интерфейс должен позволять добавить Linux (eBPF) без переписывания
   контура управления.

### 1.5 Полнота проектирования и порядок реализации

Замкнутый цикл проектируется **целиком с первого коммита**:

```
генератор стратегий  →  стенд оценки  →  бандит  →  живой трафик
      (поиск)            (проверка)     (отбор)         │
          ▲                                             │
          └──────────── наблюдения ─────────────────────┘
```

Все интерфейсы цикла определяются сразу, ничего не прикручивается задним
числом.

Реализуется в порядке зависимостей — ограничение физическое, а не
вкусовое: генератор невозможно отладить раньше стенда оценки, а стенд —
раньше работающего движка.

### 1.5.1 Два этапа поставки

Деление сделано ради безопасности отладки: вся оригинальная часть проекта
(стенд оценки, бандит, генератор) доводится в среде, где ошибка стоит одно
соединение, а не связность машины.

**Этап 0 — режим прокси (пользовательское пространство).**

- Локальный SOCKS-прокси, десинк средствами сокетов и raw-пакетов
- Драйвер не нужен; права администратора нужны только для raw-отправки
  фейков
- Сломать сеть невозможно: затрагиваются только соединения через прокси
- Отладка обычная, как у любого приложения
- Здесь строятся и доводятся: стенд оценки, бандит, генератор

**Ограничение этапа 0, которое надо проговорить:** прокси действует только
на приложения, настроенные на него. Системного охвата на этапе 0 нет.

**Этап 1 — режим перехвата (WinDivert).**

- Системный охват всего трафика
- `strategy`, `scoring`, `generator`, `control` переезжают
  **без изменений**

Вторая цена этапа 0: в пользовательском пространстве выразима **не вся**
механика. Разупорядоченные TCP-сегменты и фейки с некорректной
контрольной суммой требуют контроля над пакетами. Часть пространства
поиска недоступна, и генератор обязан это учитывать (4.7).

### 1.6 Безопасность разработки

Обязательно с самого начала:

- режим «только наблюдать» (без модификации);
- killswitch и автооткат при потере связности;
- ограниченный радиус поражения: применение стратегии к заданному
  подмножеству соединений, а не ко всему трафику сразу.

## 2. Исходное состояние и границы работы

### 2.1 Старт с чистого листа

Движок пишется с нуля. Если в репозитории присутствует ранее сделанный
фронтенд под другую архитектуру — он **припаркован**: не трогать,
не адаптировать, не удалять.

### 2.2 Только Go. Визуальный слой — не твоя зона

Оболочка, интерфейс, кнопки, вся визуальная часть реализуются владельцем
проекта самостоятельно. От тебя требуется **только движок**.

Отсюда жёсткое требование: **движок обязан быть headless.**

- Любая возможность доступна без интерфейса. Нет настроек или действий,
  доступных «только из UI».
- Движок возвращает **данные, а не представление**: никаких готовых
  подписей, цветов, человекочитаемых формулировок, предрассчитанной
  вёрстки. Форматирование — зона потребителя.
- Машинно-читаемая поверхность стабильна и документирована, чтобы на ней
  можно было построить любой интерфейс, не читая исходники.

Проектируй не «бэкенд к будущему фронту», а самостоятельный движок,
для которого интерфейс — один из возможных потребителей.

### 2.3 CLI — основная рабочая поверхность

На ближайшие месяцы единственный способ работы с движком.

```
evasion run --mode proxy       контур управления, десинк через сокеты (этап 0)
             --listen 127.0.0.1:1080
evasion run --mode intercept   контур управления, перехват пакетов (этап 1)
    --observe                   только наблюдать, не модифицировать
    --groups youtube,discord    ограничить радиус поражения
evasion probe <target>         одна проба: тайминги и форма полосы
evasion blockcheck <host>      перебор портфеля по одной цели
evasion search --budget 2h     генетический поиск в песочнице
evasion portfolio              стратегии с оценками
evasion strategy <id>          дерево стратегии в сериализованном виде
evasion replay <pcap>          офлайн-воспроизведение
evasion doctor                 проверка окружения и состояния портфеля
evasion status                 состояние работающего движка
```

**У каждой команды обязателен флаг `--json`**, и структуры вывода должны
быть продуманными, а не отладочными: именно они станут контрактом
для будущего интерфейса. Человекочитаемый вывод — отдельная ветка
форматирования, на структуры не влияет.

### 2.4 Контракт данных

Доменные типы определяешь сам. Исключение одно: **представление стратегии
как дерева примитивов фиксируется заданием** (4.3) — это единственный тип,
который мутирует генетический алгоритм, и неудачная форма здесь
потребовала бы переписать всё остальное.

### 2.5 Источник и приёмник пакетов — интерфейсы с первого коммита

```go
type PacketSource interface { Recv() (Packet, error) }
type PacketSink   interface { Send(Packet) error }
```

Реализации: WinDivert (живой режим), pcap (офлайн-воспроизведение),
синтетика (тесты). Благодаря этому логика десинка тестируется без сети
и без Windows.

Граница применимости воспроизведения:

| Инструмент | Что проверяет | Где работает |
|---|---|---|
| `replay` | корректность формируемой последовательности пакетов | офлайн, бесплатно |
| оценка приспособленности | обманулся ли DPI | только живая сеть |

Реакцию цензора на последовательность, которая никогда не отправлялась,
из записи получить нельзя. Поэтому бюджет живых прогонов — реальное
ограничение; решается параллельностью (5.4), выделенными соединениями
песочницы и пассивным сигналом (5.10).

### 2.6 Язык

- Комментарии и документация — **на русском**
- Идентификаторы, имена файлов и пакетов — на английском

### 2.7 Плотность комментариев

Правило: **плотность пропорциональна непрозрачности кода.**

Обязательно:
- док-комментарий у каждого пакета — зачем существует, что знает,
  чего знать не должен;
- док-комментарий у каждой функции, включая неэкспортируемые — что делает,
  зачем, какие неочевидные ограничения;
- густые построчные пояснения там, где код объективно непрозрачен:
  смещения байт, порядок байт, арифметика номеров последовательности TCP,
  особенности протоколов, пересчёт контрольных сумм.

Запрещено: комментарии, пересказывающие код.

```go
// ПЛОХО
i++                     // увеличиваем i
if err != nil {         // если ошибка не nil

// ХОРОШО
// Поле суммы обнуляем: оно само участвует в подсчёте,
// и старое значение исказит результат.
binary.BigEndian.PutUint16(tcp[16:18], 0)
```

В `packet`, `tlsparse`, `desync` плотность будет высокой — это нормально.
В `config` и `cli` — низкой.

## 3. Среда и ограничения

### 3.1 Формальности

- **Платформа:** Windows 10/11 x64. Без 32-бит, без Win7/8.
- **Права:** для этапа 1 запуск от администратора обязателен (драйвер).
  Для этапа 0 — только при отправке raw-пакетов. Проверка на старте
  с внятным сообщением.
- **Поставка WinDivert:** `.dll` и `.sys` рядом с бинарником, с текстом
  лицензии LGPLv3 и возможностью замены библиотеки. Только динамическое
  связывание — требование лицензии.
- **Антивирус:** документировать, что Defender может реагировать
  на драйвер перехвата. **Никаких попыток скрываться от антивируса** —
  это ровно то поведение, по которому программу считают вредоносной.
- **Зависимости:** Go 1.27, опора на стандартную библиотеку, внешние
  зависимости по минимуму, **без CGO**.

### 3.2 IPv6 — с первого дня

Оба протокола обрабатываются изначально.

Причина: если движок обрабатывает только IPv4, а приложение уйдёт
по IPv6, трафик пройдёт мимо логики. Стратегия будет выглядеть нерабочей,
хотя просто не применялась. Для генетического поиска это смертельно:
функция приспособленности получит шум вместо сигнала.

Минимально допустимая альтернатива: явное обнаружение утечки по IPv6
с отказом работать, пока она не устранена. Молча работать «наполовину»
запрещено.

### 3.3 QUIC — блокируется в первой версии

QUIC идёт по UDP, и TCP-десинк на него не влияет. Браузеры активно
используют QUIC, поэтому без обработки цель вроде YouTube будет
«не лечиться» по непонятным причинам.

Решение для v1: обнаруживать QUIC и блокировать, чтобы приложение
откатилось на TCP.

Объём и обратимость:

- блокируется **только трафик к отслеживаемым группам**, не весь UDP/443
  на машине;
- поведение настраивается и может быть выключено;
- при завершении работы блокировка **снимается полностью** — остаточных
  правил не остаётся;
- `doctor` сообщает, если приложение по признакам работает только
  по QUIC: для него блокировка означает потерю связи, а не откат на TCP.

Собственный десинк для QUIC — отдельный последующий этап. Известный минус
решения: QUIC быстрее, его блокировка слегка ухудшает то, что и так
работало.

## 4. Архитектура и границы пакетов

### 4.1 Состав пакетов

```
cmd/evasion/        CLI

internal/
├── core/            доменные типы, не импортирует ничего из проекта
├── packet/          разбор и сборка IP/TCP/UDP, контрольные суммы
├── tlsparse/        ClientHello, SNI, точки разреза записи
├── capture/         PacketSource/PacketSink + windivert, pcap, synthetic
├── flow/            таблица соединений, состояние, истечение (этап 1)
├── strategy/        дерево примитивов: представление, валидация,
│                    сериализация, реестр видов примитивов
├── desync/          семантика примитивов, построение последовательностей
├── executor/        интерфейс Executor + объявление возможностей (4.7)
├── socketexec/      исполнитель в пользовательском пространстве (этап 0)
├── packetexec/      исполнитель через перехват пакетов (этап 1)
├── proxy/           SOCKS-сервер режима прокси (этап 0)
├── policy/          какому соединению какая стратегия; горячие таблицы
├── sandbox/         выделенные соединения для кандидатов
├── generator/       генетический поиск: мутации, скрещивание, популяция
├── scoring/         бандит с распадом, пороги уверенности
├── control/         контур управления
├── probe/           активные пробы
├── vantage/         определение точки наблюдения
├── store/           SQLite: события, агрегаты, ретеншн
└── telemetry/       счётчики, кольцевой буфер, slog-handler
```

Разделения, которые нельзя схлопывать:

- **`strategy` против `desync` и `executor`** — представление отдельно
  от исполнения. Генератор работает только с представлением и про пакеты
  не знает, поэтому тестируется без сети. То же разделение независимо
  применено в Geneva: генетический алгоритм и отдельный движок исполнения
  одной стратегии (блок 11).
- **`policy` против `control`** — `policy` отвечает «какая стратегия
  этому соединению» за микросекунды по предзагруженной таблице;
  `control` эту таблицу пересчитывает, медленно и в стороне.
- **`sandbox` отдельным пакетом** — граница безопасности, ей следует быть
  явной, а не спрятанной внутри `policy`.
- **`vantage` отдельным пакетом** — формирует часть ключа любого
  наблюдения (6.1), это не деталь хранилища.

### 4.2 Три правила, задающие всё остальное

**Правило 1. В горячем пути нет ни БД, ни блокировок, ни аллокаций.**
`policy` читает неизменяемый снимок таблицы. `control` готовит новый
снимок в стороне и подменяет указатель атомарно. Читатели никогда
не ждут.

**Правило 2. Изменяемое состояние принадлежит одной горутине.**
`control` владеет оценками и решениями. CLI и прочие потребители кладут
команды в канал, а не меняют состояние напрямую. Вариант с мьютексами
работоспособен, но приводит к трудноуловимым ошибкам вида «оценка
обновилась посреди принятия решения».

**Правило 3. Трогать начало соединения и уходить с пути.**

Движку нужны только **первые пакеты** каждой TCP-сессии — те, что несут
ClientHello. Остальной поток обрабатывать не требуется.

- фильтр захвата максимально узкий;
- соединение **освобождается от перехвата** сразу после обработки
  ClientHello — не «обрабатываем и пропускаем дальше», а перестаём
  получать его пакеты вообще;
- таблица потоков хранит запись ровно столько, сколько нужно для решения.

Это главный источник стабильности существующих инструментов, и свойство
архитектурное, а не следствие аккуратного кода:

| Следствие | Почему |
|---|---|
| горячий путь крошечный | единицы пакетов на соединение, а не весь поток |
| мало состояния | значит мало ошибок в нём |
| ограниченный радиус бага | затронуто только начало соединения |
| производительность не зависит от объёма трафика | основной поток идёт мимо движка |

Обработка всего потока превращает движок в узкое место и в источник
труднодиагностируемых сбоев.

### 4.3 Представление стратегии — фиксируется заданием

Модель из Geneva: стратегия — набор правил, правило — условие срабатывания
плюс **дерево действий**. Дерево двоичное: `duplicate` и `fragment`
естественно дают две ветви, `tamper` — одну.

```go
// Strategy — то, что мутирует генератор. О пакетах не знает.
type Strategy struct {
    ID    StrategyID
    Rules []Rule
}

// Rule — при каком пакете срабатывает и что с ним делать.
type Rule struct {
    Direction Direction // исходящие / входящие
    Trigger   Trigger
    Action    *Action
}

// Action — узел двоичного дерева.
// Листья отправляют или отбрасывают, внутренние узлы преобразуют.
type Action struct {
    Kind   ActionKind // Send, Drop, Duplicate, Tamper, Fragment
    Params Params     // интерфейс; своя реализация у каждого вида
    Left   *Action
    Right  *Action    // nil у Tamper и у листьев
}
```

`Send` и `Drop` — листья: первый отправляет результат преобразований,
второй его уничтожает. Пятым примитивом `Send` не является, это
терминальная операция дерева.

**Почему двоичное дерево:** скрещивание двух стратегий — это обмен
поддеревьями, на двоичном дереве он выражается в несколько строк.
На плоской структуре скрещивание невыразимо, и генератор пришлось бы
выбросить.

**Чем платим:** `Params` интерфейсом даёт меньше статической типизации,
чем отдельные типы на каждое действие. Валидацию поэтому нужно собрать
в одном месте и покрыть тестами. Альтернатива (алгебраические типы
с визитором) типобезопаснее, но мутации и скрещивание на ней пишутся
заметно сложнее; выбор в пользу удобства генератора.

### 4.4 Переполнение таблицы соединений

При исчерпании ёмкости — **деградировать в прозрачный режим**: перестать
применять стратегии к новым соединениям, пропуская их без изменений,
и записать это в лог как аварию.

Вытеснение и отбрасывание запрещены: ломать пользователю сеть из-за
переполнения внутренней структуры недопустимо. Прозрачный режим означает
«обход не работает» — плохо, но восстановимо; оборванные соединения хуже.

### 4.5 Статусы стратегий

Состояния относятся к **стратегиям**, не к соединениям. Соединение живёт
секунды и «устареть» не может; у него есть только ссылка на применённую
стратегию, фаза и исход.

Жизненный цикл (ровно одно значение):

```
candidate   порождён генератором, не проверен
testing     проверяется в песочнице
active      применяется
benched     в портфеле, но есть лучше
degraded    работал и перестал
retired     выведен, не применять
```

Независимые признаки:

| Признак | Смысл |
|---|---|
| `freshness` | дата последней проверки и срок актуальности |
| `evidence` | объём наблюдений: достаточно / мало |
| `collateral` | побочный вред: ломает ли то, что должно работать |
| `verdict` | работает / не работает — **для каждой пары «цель × точка наблюдения»** |

**`verdict` не является единственным полем стратегии.** Поскольку оценка
привязана к точке наблюдения (6.1), у одной стратегии столько вердиктов,
сколько пар:

```
стратегия → [ (цель, точка наблюдения) → вердикт, дата проверки, объём данных ]
```

Плоское поле «работает» начало бы врать при появлении второй цели
или второй сети.

**`collateral` измеряется, а не декларируется.** Пока стратегия
применяется, параллельно проверяются **контрольные цели, которые обязаны
работать всегда**. Если они начали падать — причина в стратегии, и её надо
снимать, даже если основная цель при ней ожила. Стратегия с высоким
побочным вредом не допускается в `active` без явного разрешения владельца
проекта.

Это известный практический провал инструментов десинка: комбинация,
хорошо лечащая одну цель, способна уронить остальной трафик. Признак
должен быть числом, а не предупреждением в тексте, — иначе на него нельзя
реагировать автоматически.

### 4.6 Запуск

Только консольный запуск. Служба Windows, разделение привилегий
и автозапуск — вне области первой версии.

### 4.7 Executor и объявление возможностей

#### Две независимые оси абстракции

Их легко спутать, поэтому разделены явно:

| Ось | Что выбирает | Реализации |
|---|---|---|
| **`Executor`** | *как* стратегия воплощается | `socketexec` (прокси), `packetexec` (перехват) |
| **`PacketSource`/`Sink`** (2.5) | *откуда берутся пакеты* — только внутри `packetexec` | windivert, pcap, synthetic |

`PacketSource` — деталь пакетного исполнителя, а не альтернатива ему.

#### Интерфейс

```go
// Executor воплощает стратегию для одного соединения.
//
// Реализации различаются доступной механикой: в пользовательском
// пространстве нет контроля над отдельными сегментами TCP,
// поэтому часть примитивов там невыразима.
type Executor interface {
    // Capabilities сообщает, какие виды примитивов реализация умеет.
    // Нужно генератору, чтобы не порождать невыполнимое,
    // и валидации, чтобы отказывать явно.
    Capabilities() PrimitiveSet

    Execute(ctx context.Context, s *strategy.Strategy, c Conn) error
}
```

#### Правила

1. **Стратегия объявляет, какие примитивы ей нужны.** Вычисляется обходом
   дерева, в самом дереве не дублируется — иначе поле разойдётся
   с содержимым при мутации.
2. **Исполнитель отказывается явной ошибкой** от стратегии, которую
   не умеет. Молчаливое игнорирование непосильного примитива запрещено:
   стратегия будет оценена как нерабочая, хотя просто не применялась —
   тот же класс порчи измерений, что и утечка по IPv6 (3.2).
3. **Генератор ограничивает пространство поиска** набором возможностей
   текущего исполнителя и расширяет его автоматически при появлении более
   способного. Список берётся у исполнителя, а не задаётся константой
   (10.3).
4. **Переход между этапами не меняет `strategy`, `scoring`, `generator`
   и `control`.** Если при реализации `packetexec` потребовалось менять
   эти пакеты — абстракция спроектирована неверно.

## 5. Поведение автопилота

### 5.1 Ступенчатое допущение к трафику

Два требования задания конфликтуют напрямую: живой A/B на реальном
трафике (1.4 п. 4) и запрет генетического поиска на реальном трафике
(1.4 п. 6). Если кандидаты никогда не касаются реального трафика, живого
A/B для новых стратегий не существует.

Снимается ступенчатым допуском, по аналогии с канареечным развёртыванием:

| Статус | Допущен к | Риск для пользователя |
|---|---|---|
| `candidate` | только соединения, инициированные самим движком | нулевой |
| `testing` | доля реальных соединений (по умолчанию 5%), мгновенный откат по побочному вреду | ограниченный |
| `active` | полностью | обычный |
| `benched` | не применяется, оценка продолжает затухать | нет |

Мутанты генератора проверяются на синтетике и к реальному трафику
не допускаются. Стратегия, прошедшая порог, получает доступ к реальным
соединениям — там и происходит основное обучение.

### 5.2 Изоляция экспериментального пути

Поиск не имеет права портить состояние работающего движка.

**В режиме прокси (этап 0):** соединения песочницы устанавливает сам
движок, минуя путь пользовательских соединений. Раздельные пулы
соединений, раздельный учёт, общий только код исполнителя.

**В режиме перехвата (этап 1):** соединения песочницы инициирует движок
сам, поэтому у них собственный диапазон локальных портов. По нему они
отделяются уже на уровне захвата — **отдельным фильтром WinDivert**:

```
продуктивный:      трафик пользователя → своя таблица потоков → снимок политик (чтение)
экспериментальный: свои локальные порты → своя таблица потоков → свои кандидаты
                              ↑
                     общий только слой захвата
```

Требования изоляции в обоих режимах:

- таблицы состояний раздельные — кандидат не попадает в продуктивную;
- снимок политик продуктивного пути поиском не изменяется;
- поиск работает в своей горутине с ограниченными ресурсами;
  его сбой не должен останавливать основной путь;
- при исчерпании ресурсов останавливается поиск, а не продуктивный путь.

### 5.3 Двухуровневая оценка

Время прогонов съедают таймауты и замер полосы. Генетическому алгоритму
замер полосы не нужен — достаточно бинарного «обманулся ли DPI»,
что видно по хендшейку.

| Уровень | Содержание | Порядок времени | Потребитель |
|---|---|---|---|
| Быстрый | TCP+TLS хендшейк, вердикт по RST/зависанию | ~100 мс | генератор, отбор кандидатов |
| Медленный | форма полосы за окно | ~8 с | повышение до `active`, детект замедления |

Обязательные оптимизации:

1. **Таймаут вычисляется от измеренного базового RTT**, а не задаётся
   константой. Провал должен разрешаться примерно за секунду.
2. **Ранний вердикт**: получен RST или хендшейк завис дольше базового —
   результат зафиксирован, досиживать окно не нужно.
3. Медленный уровень применяется только к стратегиям, дошедшим
   до решения о повышении.

Порядок величин: 60 прогонов по медленному уровню последовательно —
минуты; по быстрому с восемью воркерами — меньше секунды.

### 5.4 Параллельность и её предел

Параллельность в этой архитектуре естественна: стратегия выбирается
на соединение, поэтому воркеры гоняют разные стратегии независимо.

Но за некоторым пределом параллельность **портит измерение, а не ускоряет
его**:

- много одновременных соединений к одной цели — необычный рисунок
  трафика, DPI может ответить иначе, чем на обычное поведение;
- если DPI держит состояние по IP источника, результаты параллельных
  прогонов к одной цели **коррелируют**: вместо N независимых наблюдений
  получается одно, размазанное на N.

Ограничения по умолчанию:

| Параметр | Значение |
|---|---|
| воркеров глобально | `min(8, NumCPU)`, настраивается, верхний предел 16 |
| одновременно на одну цель | 2 |
| джиттер между запусками | обязателен |

### 5.5 Порог перехода `candidate` → `testing`

Порог статистический и адаптивный. Счёт «успехов подряд» не используется:
короткую серию легко набрать случайно.

```
база: 20 наблюдений, нижняя граница доверительного интервала
      доли успехов > 0.8

эскалация требуемого объёма до 60, если:
  — исходы чередуются (успех/провал вперемешку) — признак неустойчивости
  — высокая доля inconclusive — измерению нельзя доверять
  — обнаружен побочный вред
  — стратегия ранее уже деградировала
```

Границы жёсткие: не менее 20 и не более 60. Выше 60 проверка одного
кандидата становится дороже пользы от него.

### 5.6 Режим генератора

Переключаемый, с возможностью задать период работы:

- по команде `search` с бюджетом (`--budget 2h`) — режим первой версии;
- непрерывно в фоне — включается конфигом, когда стенд оценки себя
  покажет.

Переключается настройкой, а не переписыванием кода.

### 5.7 Числовые параметры по умолчанию

Все значения — в конфиге, не в коде (блок 10).

| Параметр | По умолчанию | Смысл |
|---|---|---|
| полужизнь оценки | 6 ч | скорость забывания |
| выдержка до смены | 15 мин | защита от дребезга |
| порог превосходства | 0.15 | насколько претендент должен быть лучше |
| срыв по провалам | 3 подряд | быстрый контур реакции |
| интервал проб (норма) | 12 мин ± 40% | джиттер обязателен |
| интервал проб (деградация) | 45 с | быстрый поиск замены |
| вес ok / throttled / fail | +1 / −0.7 / −1 | градуированные исходы |
| вес inconclusive | 0 | не учитывается вообще |
| вес пассивного наблюдения | 0.3 | условия не контролируются (5.10) |
| доля соединений под `testing` | 5% | потолок жёсткий |

### 5.8 Полный обвал портфеля

Когда не работает ничего, включая резерв:

1. **прозрачный режим** — пропускать трафик без изменений;
2. **громкая тревога** в логе и в выводе `status`;
3. **разрешить повышенную долю эксперимента** — когда не работает ничего,
   риск эксперимента уже ничего не ухудшает.

Бесконечный слепой перебор запрещён: он жжёт сеть и отдаёт DPI
дополнительные данные о поведении машины.

### 5.9 Проверка при старте

Команда `evasion doctor`, запускаемая автоматически при первом пуске
и после долгого перерыва. Выводит:

- наличие необходимых прав;
- загружается ли драйвер WinDivert (для этапа 1);
- состояние утечки IPv6;
- ситуация с QUIC, включая приложения, работающие только по QUIC;
- базовая связность и измеренный RTT до контрольных целей;
- какие цели деградированы прямо сейчас;
- состояние портфеля: сколько стратегий, в каких статусах, их свежесть;
- определённая точка наблюдения;
- конфликты с другими инструментами перехвата, если запущены.

**Отдельное требование.** После долгого перерыва оценки портфеля затухли
(5.7) и доверять им нельзя. Проверка обязана сказать это прямо
и предложить перевалидацию, а не показывать устаревшие оценки как
действующие.

### 5.10 Пассивный сигнал о сбоях

Главное ограничение автопилота — бюджет живых прогонов. Активные пробы
дороги, их мало, выборка узкая.

Но часть сигнала доступна **бесплатно, со всего реального трафика**:

> Повторная отправка ClientHello — сильный признак того, что соединение
> было сорвано. Это видно пассивно, без единой пробы.

Движок обязан использовать этот источник. Что наблюдается:

- повторные отправки ClientHello: сколько и с какими интервалами;
- аномалии входящих последовательностей (в частности RST
  с характерными номерами);
- завершилось ли соединение в итоге успешно и через какое время.

Механизм не нов: определение «каким хостам нужна обработка»
по ретрансмиссиям применяется в существующих инструментах (блок 11).
Берётся как принцип, без переноса параметров.

#### Обязательная оговорка о весе

Ретрансмиссия случается и при обычной потере пакетов. Условия пассивного
наблюдения не контролируются: неизвестно, что делал канал в этот момент.

Поэтому:

- **вес одного пассивного наблюдения ниже** (5.7: 0.3 против 1);
- требуется базовая линия: обычная доля ретрансмиссий на контрольных
  целях, относительно которой аномалия и определяется;
- выводы делаются по накоплению, а не по единичному событию.

Расчёт в пользу пассивного сигнала: наблюдений больше на порядки,
и суммарно они дают больше информации, несмотря на меньший вес каждого.

## 6. Хранение данных и корпус наблюдений

### 6.1 Оценка привязана к точке наблюдения

**Оценка стратегии не является свойством стратегии.** Она свойство
четвёрки: `стратегия × цель × точка наблюдения × время`, где точка
наблюдения — оператор, регион, тип доступа (мобильный/проводной).

Поведение DPI существенно различается между операторами и регионами.
Следствия:

- ключ любого наблюдения **обязан** включать точку наблюдения;
- вопрос «работает ли стратегия X» без указания, у кого именно,
  не имеет ответа;
- тестирующий сервер в датацентре находится за другим DPI и измеряет
  цензуру датацентра, а не пользователя. Один хост как фоновый тестер
  даёт сведения о себе. Полезен он только как часть распределённой
  системы измерений — отдельный, значительно больший этап.

### 6.2 Как определяется точка наблюдения

**Внешних запросов по умолчанию нет.** Это требование согласовано
с 6.6: определение точки наблюдения не должно само становиться утечкой.

Порядок:

1. **Метка из конфига** — основной способ. Владелец проекта указывает
   оператора, регион и тип доступа сам.
2. **Локальные признаки** — параметры интерфейса, шлюз по умолчанию,
   суффикс DNS. Используются как подсказка и для обнаружения смены сети.
3. **Внешнее определение** (запрос собственного публичного IP, ASN) —
   **только по явному включению**, по умолчанию выключено.

При смене сети точка наблюдения меняется, и оценки другой точки
применять нельзя — это должно быть видно в `status` и `doctor`.

### 6.3 Три слоя по характеру доступа

Единая «массивная база», обслуживающая всё, — неверная модель: характеры
обращения несовместимы.

```
горячий путь ──► структуры в памяти (без БД)
                      ▲
                      │ асинхронная загрузка
приём ──► журнал событий (только добавление)
                      │
                      ▼
            материализованные срезы ──► аналитика и решения
```

1. **Горячий путь** — решение при ClientHello. **Не обращается к БД
   никогда.** Только предзагруженные структуры в памяти, обновляемые
   асинхронно.
2. **Приём телеметрии** — только добавление, без обновлений, пакетная
   запись, разбиение по времени.
3. **Аналитика** — сканирование истории, считается отдельно от приёма.

Отдельные «подбазы» — это **материализованные представления**:
предрассчитанные срезы вида «стратегия × цель × оператор × час → доля
успехов». Они снимают конкуренцию тяжёлых запросов с приёмом данных,
ради чего разделение и затевается.

### 6.4 Что получает строку, а что счётчик

Без этого правила объём данных неконтролируем: на активной машине
соединений десятки тысяч в сутки.

**Отдельная строка пишется только для:**

- соединений, к которым применялась стратегия;
- соединений с обнаруженной аномалией (ретрансмиссии, RST);
- результатов активных проб;
- событий жизненного цикла стратегий и переключений.

**Всё остальное — только агрегированные счётчики** (количества
по группам, исходам, интервалам времени). Строка на каждое соединение
машины не пишется никогда.

Оценка объёма при таком правиле: единицы тысяч строк в сутки
по ~200 байт — до ~2 МБ/сутки, порядка 0.7 ГБ/год. SQLite справляется.

**Ретеншн обязателен, а не желателен:**

| Данные | Срок по умолчанию |
|---|---|
| сырые строки соединений и проб | 30 суток |
| агрегированные срезы | 1 год |
| события стратегий | бессрочно (объём мал) |

Сроки настраиваются. Удаление автоматическое, без ручного вмешательства.

### 6.5 Выбор хранилища

- **Сейчас: SQLite** — один писатель, WAL, пакетная запись. Что-либо
  «массивное» на этом этапе — преждевременное усложнение, которое ничего
  не ускорит.
- **Позже, при распределённом сборе** — колоночная СУБД под аналитическую
  нагрузку (уместна ClickHouse). Отдельный этап.
- **Схема проектируется под возможность перехода:** события без
  обновлений, явные временные разделы, никаких зависимостей
  от особенностей SQLite.

### 6.6 Требования к сбору при выносе на хост

База «кто какие обходы проверял, из какой сети, когда» — чувствительный
набор данных. Закладывается сразу:

- сбор **только по явному согласию**, по умолчанию выключен;
- наверх уходят **агрегаты**, не сырые записи;
- точка наблюдения обозначается грубо (оператор, регион), без адресов
  и идентификаторов машины;
- не хранить данные, не нужные для оценки стратегий;
- ретеншн с автоматическим удалением устаревшего.

Требование не только к безопасности: агрегаты компактнее, передавать
дешевле, аналитика по ним быстрее.

## 7. Наблюдаемость и логирование

Терминология: **туннелей в проекте нет.** Логируются **соединения**.

Наивное «логировать каждый отправленный пакет» убьёт движок:
на горячем пути десятки тысяч событий в секунду, и форматирование строк
там дороже самой обработки. Поэтому три слоя:

| Слой | Содержание | Стоимость |
|---|---|---|
| Всегда включено | счётчики: пакетов, по стратегиям, по исходам | атомарные инкременты |
| Всегда включено | жизненный цикл соединения: открытие, ClientHello, применённая стратегия, исход, закрытие | единицы событий на соединение |
| По явному включению | подробности по каждому пакету | только отладочный режим, с ограничением частоты |

**Кольцевой буфер** последних событий в памяти: 10 000 записей
по умолчанию, настраивается. Нужен, чтобы после сбоя увидеть, что
происходило прямо перед ним, не включая отладку заранее.

Логи структурированные (`log/slog`), поля машинно-читаемые.

## 8. Качество кода, тесты и приёмка

### 8.1 Производительность — измеримая, не декларативная

Требование максимальной оптимизации формулируется как проверяемые
бюджеты, иначе оно конфликтует с требованием корректности: предельная
оптимизация означает небезопасные приёмы и нечитаемый код, то есть
**больше** багов, а не меньше.

Начальные бюджеты:

| Путь | Бюджет | Аллокации |
|---|---|---|
| проверка «интересно ли это соединение» | ≤ 1 мкс | 0 |
| решение по ClientHello (разбор + политика + выбор стратегии) | ≤ 10 мкс, p99 | 0 |

Правила:

- бюджеты **подтверждаются бенчмарком** на целевой машине; если
  недостижимы — сообщить с замерами, а не молча превысить;
- ноль аллокаций проверяется `testing.AllocsPerRun`, а не визуально;
- бенчмарки обязательны для пакетного слоя, регресс ловится в CI;
- **везде, кроме горячего пути, — прямолинейный скучный код.**
  Оптимизация без предварительного замера запрещена.

### 8.2 Корректность

Для пакетного и протокольного кода это важнее любой оптимизации:

- **Фаззинг обязателен** для всех парсеров (встроенный в Go). Разбор
  пакетов и TLS — самое выгодное место для фаззинга во всём проекте.
- Никаких `panic` в пакетном пути. Все обращения к байтам — с проверкой
  границ.
- `go test -race` обязателен.
- Золотые тесты на построение последовательностей пакетов.
- Данные из сети считаются враждебными всегда.
- Статический анализ: `go vet`, `staticcheck`.

### 8.3 Приёмочный критерий: офлайн-тесты раньше интеграции

Отладка ошибок пакетного уровня по живой сети практически невозможна:
неизвестно, виноват свой код или изменившееся поведение DPI.

Поэтому требование сформулировано как **порядок работ**:

> Примитивы десинка реализуются против **синтетического источника**
> (2.5), и золотые тесты на формируемую последовательность пакетов
> обязаны существовать **до** начала интеграции с WinDivert.
> Интеграция не считается начатой, пока их нет.

Воспроизведение становится режимом разработки по умолчанию, а не
отдельной задачей, которую можно сдвинуть.

#### Обязательный набор проверок последовательностей

- корректность номеров последовательности TCP при разрезании
  и дублировании;
- корректность контрольных сумм после любой правки заголовков;
- **значения TTL при повторной отправке**: фейк, отправленный с низким
  TTL, при ретрансмиссии не должен уходить с обычным TTL — известный
  класс ошибок в инструментах такого рода, глазами не обнаруживается;
- поведение при обрезанном или некорректном ClientHello;
- отсутствие изменений в потоке после освобождения соединения
  от перехвата (правило 3 в 4.2).

### 8.4 Когда пакет считается готовым

Пакет завершён, если выполнено всё:

1. док-комментарии по 2.7;
2. юнит-тесты на публичное поведение, включая крайние случаи;
3. фаззинг — для всего, что разбирает внешние данные;
4. бенчмарк и проверка аллокаций — для горячего пути;
5. `go vet`, `staticcheck`, `go test -race` без замечаний;
6. не осталось `TODO` и заглушек, возвращающих пустые значения;
7. если пакет виден в CLI — структуры `--json` описаны.

## 9. Протокол работы

### 9.1 Уточнять до того, как писать

**Перед любой правкой или созданием кода — сначала уточнить, что именно
требуется.** Не начинать писать по догадке. Если задача допускает
несколько прочтений, задать вопрос и дождаться ответа.

Это касается и правок существующего кода: прежде чем менять, объяснить,
что именно и почему меняется.

### 9.2 Пояснять каждое изменение

По каждому создаваемому или изменяемому фрагменту:

- **что** делается;
- **зачем** — какую задачу решает;
- **какие были альтернативы** и почему выбрана эта;
- **чем заплатили** — какие недостатки у выбранного решения.

Последний пункт обязателен. Решение без названной цены означает, что цена
не продумана.

### 9.3 Объективная оценка, без самопохвалы

- Не называть собственный код «оптимальным», «надёжным»,
  «production-ready» без оснований. Основание — замер или тест,
  а не формулировка.
- Если оптимизация не нужна — говорить прямо, что не нужна, вместо того
  чтобы придумывать улучшения ради видимости работы.
- Если требование владельца проекта вредно — сказать об этом и объяснить
  почему, а не выполнять молча.
- Если что-то не проверено — говорить, что не проверено. Успешная
  компиляция не является доказательством работоспособности.

### 9.4 Темп и порядок работы

Один пакет за раз, с паузой на ревью владельцем проекта между пакетами.
Не выдавать большие объёмы кода разом: код должен быть понят, а не просто
получен — проект предполагается развивать самостоятельно.

Порядок реализации — по зависимостям:

**Этап 0 (режим прокси):**

| Шаг | Содержание | Результат |
|---|---|---|
| M0 | `core`, `strategy` (представление, валидация, сериализация, реестр) | стратегии описываются и проверяются |
| M1 | `packet`, `tlsparse` + фаззинг + золотые тесты | разбор и сборка работают |
| M2 | `desync`, `executor`, `socketexec` против синтетики | примитивы исполняются и проверены офлайн |
| M3 | `proxy` | **первый работающий обход** |
| M4 | `probe` (двухуровневая оценка), `vantage` | измерения с честной классификацией |
| M5 | `store`, `telemetry` | наблюдения сохраняются |
| M6 | `scoring`, `policy`, `control` | **автопилот работает** |
| M7 | `sandbox`, `generator` | **поиск стратегий работает** |

**Этап 1 (режим перехвата):**

| Шаг | Содержание | Результат |
|---|---|---|
| M8 | `capture` (windivert, pcap), `packetexec` | перехват и воспроизведение |
| M9 | `flow` + правило раннего освобождения (4.2) | устойчивый пакетный путь |
| M10 | перевод `control` на `packetexec` | **системный охват** |

При переходе к M8–M10 пакеты M0, M6, M7 изменяться не должны (4.7 п. 4).

## 10. Адаптируемость

### 10.1 Никаких магических чисел в коде

Всё, что в задании названо значением по умолчанию, живёт в конфигурации.
В коде допустимы только константы, вытекающие из протоколов (размеры
заголовков, границы полей).

Из конфига задаются как минимум: параметры 5.7, число воркеров и пределы
параллельности (5.4), пороги повышения (5.5), доля экспериментальных
соединений, цели проб, контрольные цели, группы доменов, бюджеты 8.1,
сроки ретеншна (6.4), метка точки наблюдения (6.2).

### 10.2 Стратегии сериализуемы

Дерево стратегии должно читаться из конфига и записываться в него.
Следствия, каждое нужно на практике:

- стратегию можно написать рукой и проверить;
- найденную генератором — выгрузить, сохранить, перенести на другую
  машину;
- портфель хранить в виде данных, а не кода;
- при разборе внешнего описания оно считается **недоверенным**
  и проходит полную валидацию.

### 10.3 Реестр примитивов, а не их перечисление в коде

Генератор **не содержит захардкоженного списка действий.** Он получает
доступные виды примитивов из реестра в `strategy` и пересекает
с возможностями исполнителя (4.7).

Практический смысл: добавление нового примитива автоматически расширяет
пространство поиска, и генератор при этом не меняется. Касаться нужно
только `desync` (исполнение) и валидации в `strategy`.

Это главное требование к адаптируемости: пространство стратегий растёт
без переписывания того, что его обходит.

### 10.4 Расширяемые точки

Должны добавляться без изменения контура управления:

- новая реализация `Executor` (4.7);
- новая реализация `PacketSource`/`PacketSink` (2.5);
- новый вид примитива (10.3);
- новая цель или группа целей (конфиг);
- новое хранилище (6.5) — через интерфейс, без зависимости
  от особенностей SQLite.

### 10.5 Перечитывание конфигурации

Параметры автопилота (5.7), цели и пороги применяются без перезапуска.
Параметры, требующие перезапуска (фильтры захвата, диапазоны портов,
адрес прослушивания прокси), должны быть явно перечислены
в документации — чтобы не выяснялось опытным путём.
