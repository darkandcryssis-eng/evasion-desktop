# Discord через встроенный движок: рабочий рецепт

Как поднять Discord (вход, текст, картинки, голос, демонстрация экрана) через
встроенный движок обхода DPI, без внешних VPN. Проверено на реальном
провайдере с TSPU.

## Запуск в один клик

```
scripts\start-discord.bat
```

Скрипт (запросит права администратора сам):

1. собирает свежий `evasion.exe` из исходников (если установлен Go);
2. поднимает движок в отдельном окне с нужными флагами;
3. закрывает Discord и запускает заново с выключенным DoH.

Окно `movok-engine` не закрывать, пока пользуешься Discord.

> Должен работать **ровно один** `evasion.exe`. Параллельные экземпляры
> конфликтуют за WinDivert handle на одних пакетах — соединения рвутся,
> голос зависает на `AUTHENTICATING`. Лаунчер сам глушит старые перед
> стартом. Проверить вручную: `taskkill /F /IM evasion.exe` до запуска.

## Что нужно один раз

1. **Собрать бинарник** (не обязательно вручную — лаунчер делает сам):

   ```
   set "GOTOOLCHAIN=go1.27.2"
   go build -o evasion.exe .\cmd\evasion
   ```

   > Не писать это одной строкой через `&&`: cmd захватывает пробел перед
   > `&&` в значение переменной, и `go` молча падает с
   > `non-semver module version "...go1.27.2 ..."`.

2. **Положить рядом** `WinDivert.dll` и `WinDivert64.sys`.

3. **(Опционально) hosts-подмена** для доменов с заблокированным IP —
   выполняется автоматически при запуске движка, если в конфиге включён
   `transport_fallback.enabled: true`. Снять: `evasion.exe hosts clean`.

## Карта блокировки

Discord обслуживается Cloudflare из блока `162.159.128.0/22`. Провайдер
режет по двум осям:

### Ось 1 — IP-блок по суффиксу адреса

| домен | IP Cloudflare | обход |
|-------|---------------|-------|
| `discord.com`, API | работают сами | не нужен |
| `gateway.discord.gg` (`.234`) | IP режут | hosts → `162.159.138.232` |
| `cdn.discordapp.com` (`.233`) | IP работает, SNI режут | десинк `tcp_overlap` |
| `media.discordapp.net` (`.232`) | работает | hosts → `162.159.138.232` |
| `*.discord.media` (`.234`/`.235`) | работают | десинк voice-handshake |

`transport_fallback` в `examples/config.json` подменяет `gateway.discord.gg`
и `media.discordapp.net` на `162.159.138.232` — Cloudflare any-IP routing
по SNI, запрос доедет до нужной службы. Для `cdn.discordapp.com`
hosts-подмена **не помогает**: там блокировка на уровне TLS SNI, нужен
десинк.

### Ось 2 — DPI по TLS ClientHello

**Стратегия по размеру ClientHello**:

- маленький (нативный апдейтер, curl) → `disorder-sni` (reverse
  fragment по SNI);
- большой (Chromium: веб-апп, gateway, голос — GREASE/ECH/много
  расширений) → `fake-badsum`-подобные схемы: `disorder-sni` ломает его
  (Cloudflare не склеивает обратно → RST);
- `discord.com` DPI не трогает — ему десинк вообще не нужен.

Стратегии по группам в `examples/config.json`:

| группа | домены | стратегия |
|--------|--------|-----------|
| `discord_updates` | `updates.discord.com` | `disorder-sni` |
| `discord_gateway` | `gateway.discord.gg` | fallback (+ hosts-reroute) |
| `discord_voice` | `discord.media` | **`badseq` + apple-ClientHello + `split-sni`** |
| `discord_cdn` | `cdn.discordapp.com`, `discordapp.net` | **`tcp_overlap` с cover-пресетом** |
| (вне радиуса) | `discord.com` | без десинка |

Голосовой control-plane (WSS к `*.discord.media`) — самый плотный рецепт:

- **фейк несёт БЕЗОБИДНЫЙ ClientHello** (preset `tls_clienthello_apple` в
  `internal/tlsfake`), а не копию настоящего. Если фейк — копия, в нём
  открытым текстом тот же SNI `discord.media`, DPI видит ровно тот
  сигнал, от которого прячемся.
- **обман TCP `badseq` (seq фейка сдвинут на -10 000), НЕ `badsum`**.
  На Windows сетевые карты часто выгружают пересчёт TCP checksum на
  железо — битая сумма чинится до выхода, фейк доходит до сервера
  целым и ломает рукопожатие (`net_error -113`). `badseq` работает на
  уровне последовательности: сервер отбрасывает по TCP, а не по сумме.
- **плюс сплит настоящего hello по SNI** (`fragment inside_sni forward`).
  Один слой десинка рукопожатие иногда переживало, два — не оставляет
  шансов.

Применяется ко всем RTC-портам одинаково, порты не блокируем,
`--rtc-redirect` выключен.

### CDN через `tcp_overlap`

У `cdn.discordapp.com` стандартные TLS-десинк схемы не работают: имя остаётся
в reassemble'нной склейке независимо от фрагментации, TSPU видит его и RST'ит.
Приём `tcp_overlap`:

1. Движок удерживает оригинальный ClientHello (`seq=SN`, размер `L`).
2. Шлёт cover-пакет: 681-байтный безобидный ClientHello с `seq = SN + L - 681`
   — перекрывает по TCP sequence последние 681 байт настоящей нагрузки.
3. Шлёт настоящую нагрузку (`seq = SN`), покрывая [SN..SN+L].

Сервер по правилу TCP overlap собирает оригинальный ClientHello целиком
(RFC 1122, «последний пришедший перезаписывает»). DPI парсит cover первым
по порядку прибытия, классифицирует соединение по безобидному SNI, пропускает.
Настоящий SNI остаётся невидимым.

### DoH обходит hosts

Discord (Chromium) при системном DNS `1.1.1.1` сам включает DNS-over-HTTPS и
резолвит мимо `hosts` — наша подмена гейтвея до него не доходит. Решение:
запускать с `--disable-features=DnsOverHttps` (лаунчер делает автоматически).

### RTC на «дружественных портах»

Голос и демонстрация подключаются к `*.discord.media` не только на `:443`,
но и на `2053 / 2083 / 2087 / 2096 / 8443`. Фильтр перехвата (`cmd/evasion/
intercept.go`) ловит все эти порты, иначе RTC на альт-портах шёл бы мимо
десинка.

### Голосовой UDP-медиа

Control-сокет голоса (WSS) — TCP, его чинит основной контур. Звук идёт
отдельно, по UDP к медиа-серверу, без TLS и без SNI. Если UDP не трогать,
TSPU опознаёт его по первому пакету (IP discovery, 74 байта, тип `0x0001`)
и душит медиа. Симптом: канал цепляется, доходит до `READY`, через ~15 сек
WSS падает (`code 1006` / `4801 Cannot resume`) и цикл повторяется.

Лечится десинком голосового UDP (`--voice` у `run`): перед настоящим пакетом
IP discovery движок шлёт 6 decoy с нейтральной нагрузкой и коротким TTL.
Они доходят до DPI, но умирают до сервера. DPI видит в начале потока
«посторонние» пакеты, не опознаёт голос и не трогает ни IP discovery, ни
последующий RTP.

Детали:

- **порт**: медиа-порт не только `50000+`. На Cloudflare-фронтовых RTC-
  серверах он в диапазоне `19294–19344` (в логах — `:19327`). Фильтр ловит
  весь исходящий UDP, кроме `:443` (`cmd/evasion/voicedesync.go`).
- **включение**: `--voice ttl` — дефолт для `run` (с ноября 2026). Лаунчер
  тоже передаёт этот флаг явно.
- **демонстрация экрана**: поток WebRTC открывается не IP discovery, а
  запросом STUN Binding. Он получает те же decoy, но только на медиа-портах
  Discord (`19294–19344` кроме `19302` — публичный STUN Google, `50000–50100`).
  Голос и каждый стрим — отдельные control-соединения к одному серверу,
  поэтому «дёрганым» сервер считается с шести ClientHello за две минуты.
- **альтернативы**: если `ttl` не держит голос у конкретного провайдера,
  пробуй `--voice badsum`. Приём подбирается живой пробой.

### Переклейка душимых RTC-портов

`--rtc-redirect` выключен по умолчанию: смена порта даёт `4006 Session is
no longer valid` (Discord привязывает сессию к порту, на другом порту тот
же сервер её не знает). Флаг оставлен в движке для экспериментов, но лаунчер
его не передаёт.

## Известные ограничения

- Часть RTC-серверов в отдельных регионах иногда не доходит до `READY`.
  Обход: в настройках голосового канала задать Region Override
  (Stockholm/Finland обычно работают).
- `--voice` подбирается под провайдера: если `ttl` не держит голос, пробуй
  `badsum`. TTL-decoy выбирает TTL по наблюдаемому числу хопов до сервера;
  если наблюдений ещё нет, используется резервное значение 6. Это рассчитано
  на то, что DPI ближе сервера; на нетипичной топологии может потребоваться другой режим.
- Для `cdn.discordapp.com` `tcp_overlap` работает если настоящий ClientHello
  длиннее 681 байт (все современные Chromium — да). Короткие ClientHello
  (нативный Discord update API) идут через fallback-стратегию.
