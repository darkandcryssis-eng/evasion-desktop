# Выполнено

## Волна «автообход дёргающегося голосового сервера» — ноябрь 2026 (ветка `feat/voice-churn-avoid`)

Запрос: пользователь ничего не должен делать руками — движок сам должен
отбраковывать плохой голосовой сервер. Полный авто-переключатель региона
невозможен (Override Region — настройка канала на стороне аккаунта Discord, за
TLS, требует прав Manage Channel), но ту же цель даёт автоматическая
отбраковка дёргающегося сервера.

Симптом: входящий медиа-поток к части стокгольмских `c-arnNN-*.discord.media`
режется TSPU. Control-сокет поднимается, канал входит, но голоса нет
(heartbeat `last received sequence number: -1`), через ~15 сек обрыв (`1006` /
`4801 Cannot resume`), Discord переподключается к ТОМУ ЖЕ серверу по кругу —
бесконечный «вход/выход». Сервер сам не меняется, пока Discord не упрётся.

Решение (`cmd/evasion/voice_churn.go`): `voiceChurn` считает ClientHello по
каждому `*.discord.media` SNI в скользящем окне. Цикл переподключений к одному
серверу рекуррентно бьёт по ОДНОМУ SNI (в поле: `4801` к тому же
`c-arnNN-*` раз в ~15-20 сек), поэтому ≥3 ClientHello за 60 сек к одному SNI =
дёрганье. Такой SNI помечается обходимым на 90 сек (TTL): движок пропускает
его сырьём (реализует `intercept.Blocklist`), DPI рвёт control-сокет сразу,
Discord быстрее упирается и просит у гейтвея ДРУГОЙ сервер, вместо минуты на
мёртвом. Пометка временная — по TTL сервер снова получает честную попытку
десинка (не вечный бан, состояние не персистится).

Безопасность радиуса: детектор действует ТОЛЬКО на `*.discord.media`. CDN,
gateway и прочий HTTPS он не трогает никогда (и Observe, и Contains жёстко
ограничены голосовым суффиксом) — пропуск CDN сырьём означал бы утечку SNI и
обрыв картинок, ровно ту регрессию, что чинили в сборке. Два источника блока
(rtctrack-based `rtcBlocklist` и живой `voiceChurn`) объединены `anyBlocklist`.

Пороги консервативны (здоровый голос — ОДИН ClientHello на весь звонок;
channel-switch идёт на РАЗНЫЕ серверы, по одному SNI не копится). Тесты
(`voice_churn_test.go`): срабатывание на пороге, НЕ-срабатывание на не-голосе
(CDN/gateway) при любом числе ClientHello, отбрасывание по окну, снятие по TTL,
объединение блок-листов.

Проверка: `go build`/`go vet` чисто, `go test -race -count=1 ./...` зелёный.
Голосовую стратегию и hosts НЕ трогает — только добавляет быстрый отказ по
дёрганью. Пороги подбираются по полевым логам (окно/порог/TTL — константы в
`voice_churn.go`).


## Волна «детектор ClientHello: нестрогий разбор при любой ошибке строгого» — ноябрь 2026 (ветка `fix/detector-lenient-first`)

Добивание остатка `не_tls` после PR #36. Полевая разбивка показала стабильные
3 пропуска `не_tls`, причём это НЕ фрагментация (её PR #36 уже чинит) — значит
строгий разбор спотыкается по другой причине (например, редкое/нестандартное
расширение ПОСЛЕ server_name), хотя имя уже корректно видно.

Корень: `TLSHelloDetector` (`internal/intercept/tls.go`) пробовал нестрогий
разбор только при `ErrIncomplete`/`ErrFragmentedHandshake`. Любая другая
жёсткая ошибка строгого разбора (`ErrMalformed` и пр.) сразу давала
`isTLS=false` → сборка сдавалась → SNI утекал.

Правка: детектор теперь СНАЧАЛА пытается применить — если имя видно (строгим
разбором либо, при любой его ошибке, нестрогим), десинк применим немедленно.
Нестрогий разбор доверяется при любой ошибке: он валидирует структуру
`server_name` и на мусоре имя не выдаёт, поэтому ложного десинка не-ClientHello
нет. Решение «ждать или пропустить» (когда имени ещё нет) по-прежнему зависит
от типа ошибки: `ErrIncomplete`/`ErrFragmentedHandshake` → ждём следующий
сегмент, остальное → не наш ClientHello, уходим с пути.

Тесты (`internal/intercept/tls_test.go`):
`TestDetectorStrictFailsAfterSNIStillApplies` — ClientHello с плохим
расширением после имени (строгий разбор даёт `ErrMalformed`, не неполноту)
теперь применяется, SNI и точки разреза извлекаются;
`TestDetectorGarbageStillNotTLS` — мусор без корректного `server_name`
по-прежнему честно «не TLS» (обобщение не даёт ложных десинков). Старые тесты
детектора (целый hello, первый сегмент с/без SNI, не-TLS, фрагментация) целы.

Проверка: `go build`/`go vet` чисто, `go test -race -count=1 ./...` — все
пакеты зелёные. Если в поле `не_tls` после этого НЕ уйдёт в ноль — значит
оставшиеся потоки реально не ClientHello (нестрогий разбор имени не нашёл) и
пропускаются верно.


Журнал закрытых работ. Каждая запись соответствует смёрженной ветке; подробности
стратегий голоса и теория блокировок — в `docs/discord-ru.md`, архитектурный
дневник решений — в `.kiro/steering/progress.md`, инварианты и план волн — в
`docs/ARCHITECTURE.md`.

Хронология — от свежего к старому (как в `git log --merges`).

## Волна «варианты cover-пресета + tcp_overlap в генераторе» — ноябрь 2026 (ветка `feat/wave2-cover-presets`)

Закрыты Волна 2 (пресеты) и пункт «генератор не умеет мутировать
ActionTCPOverlap» из `docs/ARCHITECTURE.md`. Автономный безопасный батч
(A+B): offline-проверяемо, поведение `main` не меняется, пока стратегия не
сошлётся на новое имя.

**A — варианты cover-пресета.** Базовый `tls_cover_681` (встроенный
`tls_cover_681.bin`, SNI google) дополнен тремя вариантами ТОГО ЖЕ размера
681 байт с другими SNI: `tls_cover_681_apple`, `tls_cover_681_microsoft`,
`tls_cover_681_yandex`. Зачем: один google-cover на всех соединениях сам
становится сигнатурой обхода (DPI может выучить «681 байт + google-SNI +
фиксированный набор расширений = инструмент»); варианты размывают подпись и
выглядят как разные браузеры. Для `ActionTCPOverlap` взаимозаменяемы —
смещение cover'а считается как L − M, M у всех = 681.

Варианты собираются в коде (`tlsfake/cover681_variants.go`,
`buildCover681`), а не отдельными `.bin`: берётся обычный ClientHello с
нужным SNI и добивается до ровно 681 байт расширением padding (RFC 7685,
тип 21, тело — нули). Так SNI любой длины укладывается в единый размер, и
не нужно хранить три новых блоба. `buildClientHello` отрефакторен в
`buildClientHelloExt(sni, extraExt)` — старое поведение (без добавок)
сохранено один-в-один. Реестр: новые имена в `strategy.FakePresetNames()`
и `fakePresets`; добавлен `strategy.CoverPresetNames()` — подмножество
cover-пресетов фиксированного размера. Пример:
`examples/strategies/tcp-overlap-cover-variant.json` (использует
`tls_cover_681_yandex`).

**B — tcp_overlap в генераторе.** Генетический поиск (`internal/generator`)
теперь порождает и мутирует `ActionTCPOverlap`, но ТОЛЬКО при наличии
возможности `CapTCPOverlap` (в сокетном пространстве приём неисполним, его
не порождаем). Пресет берётся из `CoverPresetNames()` — перебираются лишь
cover-пресеты фиксированного размера, иначе overlap сбился бы по длине.
Критичная правка: `cloneParams` теперь копирует `*TCPOverlapParams` (без неё
мутация/скрещивание теряли пресет и плодили невалидные узлы). `hasParams` и
`remakeParams` расширены на tcp_overlap.

Тесты на реальных байтах: `internal/tlsfake` (размер всех вариантов ровно
681, валидность TLS-записи, присутствие нужного SNI, независимые копии,
различие вариантов между собой и от базового), `internal/strategy`
(регистрация и размер cover-пресетов, приём их валидацией tcp_overlap,
присутствие в `FakePresetNames`), `internal/generator` (tcp_overlap
порождается при CapTCPOverlap и НЕ порождается без неё, корректный пресет,
отсутствие ветвей у листа, сохранность пресета через clone, корректность
мутации/скрещивания с overlap в наборе).

Проверка: `go build`/`go vet` чисто, `go test -race -count=1 ./...` — все
пакеты зелёные. Существующие тесты генератора не затронуты: их `fullCaps()`
не содержит `CapTCPOverlap`, значит tcp_overlap у них по-прежнему не
порождается.

**Крайние значения и фаз-тест tcp_overlap** (тем же батчем, пункт из «Прочее»
`CONTINUE.md`). До этого `walkTCPOverlap` на уровне `internal/desync` не был
покрыт вовсе (только косвенно через intercept/packetexec). Добавлено:
`internal/desync/tcpoverlap_test.go` — геометрия смещений рабочего случая
(cover первым со смещением L-M, настоящая нагрузка второй со смещением 0, обе
OpSendReal), крайние случаи M==L / M>L / пустая нагрузка L=0 → все дают
`ErrCutUnavailable` (а не молчаливый пропуск, портящий измерения), граница
L=M+1 (минимальное рабочее перекрытие), и инвариант одинаковой геометрии для
всех cover-вариантов (один размер 681). Фаззер `FuzzBuildPlan` (`growTree`)
теперь порождает и tcp_overlap — обход не паникует ни на коротком входе
(ErrCutUnavailable), ни на длинном (реальный план); 139k прогонов чисто.

**Полевой факт из этой сессии (для будущей работы над голосом, НЕ закрыт).**
В журнале движка (`state/events.jsonl` и stdout) при старте Discord виден
устойчивый показатель `многосегментных_пропущено=3`, не меняющийся всю
сессию: три многосегментных ClientHello движок не собирает и пропускает
сырьём, Chrome их ретранслирует (`повторов_clienthello` растёт 17→52).
Это и есть источник части RST на `cdn.discordapp.com` (`net_error -101`).
Правка — в пути сборки многосегментных hello (`applyAssembled`), горячий
путь, требует полевой проверки → это задача сессии C, а не автономного
батча. Диверсификация cover'а (эта волна) закрывает другой риск
(распознавание паттерна), а не эти три пропуска.

## Волна «сборка ClientHello терпит ретрансмиссию» — ноябрь 2026 (ветка `fix/cdn-assembly-retransmit`)

**Симптом.** GUI Discord снова долго прогружался, картинки/Rive с
`cdn.discordapp.com` сыпались `net_error -101`. В журнале движка
`многосегментных_пропущено` подскочил с 3 до 10 под нагрузкой: движок не мог
собрать многосегментный ClientHello и отдавал его сырьём → TSPU видел открытый
SNI и рвал соединение.

**Корень.** Сборщик многосегментного ClientHello (`internal/flow`,
`Table.assemble`) сдавался на ЛЮБОМ сегменте, чей seq не продолжал склейку
ровно (`seq != baseSeq+len(buf)`). Но мы САМИ провоцируем повтор: придержав
первый сегмент (Buffering), мы не даём ему уйти к серверу, сервер его не
подтверждает, и клиент по RTO шлёт тот же сегмент заново (тот же seq). Старый
строгий тест принимал этот повтор за «разрыв» и сдавался — настоящий
ClientHello уходил сырым. Чем больше параллельных CDN-рукопожатий при старте,
тем чаще повтор обгонял второй сегмент — отсюда скачок пропусков.

**Правка.** `assemble` теперь разбирает отклонение seq по типу (кольцевая
арифметика RFC 1982, `seqLE`/`seqLT`):

- повтор уже удержанных байт (ретрансмиссия) — гасится (в сеть не идёт, мы
  держим оригинал), склейка жива, ждём недостающий сегмент;
- коалесцированный повтор (несёт удержанный сегмент И следующий) — добавляет
  только новый хвост;
- разрыв ВПЕРЁД (переупорядочение) или сегмент левее начала склейки — как и
  прежде, сдаёмся (склеить без спекуляции нельзя);
- если недостающий сегмент так и не приходит, а повторы идут вхолостую —
  после `maxAssemblyStalls=8` сдаёмся и досылаем удержанное (не висим вечно).

Нормальный случай (второй сегмент приходит в том же флайте, до RTO) не
затронут — холостых повторов там ноль.

Тесты (`internal/flow/flow_test.go`): `TestAssemblyToleratesRetransmit`
(повтор не срывает сборку, настоящий сегмент её завершает),
`TestAssemblyToleratesCoalescedRetransmit` (добавляется только хвост, байты не
потеряны/не задвоены), `TestAssemblyGivesUpAfterStallLimit` (предел холостых
повторов → досылка удержанного). Старые инварианты целы:
`TestAssemblyBreaksOnSequenceGap` (разрыв вперёд по-прежнему сдаётся),
`TestAssemblyGivesUpAtSegmentLimit`, сборочные тесты intercept.

Проверка: `go build`/`go vet` чисто, `go test -race -count=1 ./...` — все
пакеты зелёные. Голосовая стратегия, hosts и cover-пресеты не затронуты.

**Полевой результат.** После фикса в журнале движка `повторов_clienthello`
рухнул с 22+ до 1, `многосегментных_пропущено` — с 10 до 3, шторм
`net_error -101` на `cdn.discordapp.com` исчез полностью, GUI грузится. Остаток
в 3 пропуска — уже НЕ от ретрансмиссий (их почти нет), причина другая.

**Диагностика причин пропуска (тем же PR).** Чтобы остаток чинить прицельно,
а не вслепую, причина отказа сборки прокинута в журнал. `flow.Action` получил
поле `Reason` (`GiveUpReason`), `giveUp` проставляет её на каждом пути:
`GiveUpSeqGap` (разрыв вперёд/левее базы), `GiveUpStall` (холостые повторы
исчерпаны), `GiveUpSegments`/`GiveUpBytes` (лимиты), `GiveUpNotTLS`. Движок
(`internal/intercept/engine.go`) копит разбивку по причинам и печатает её в
сводке полем `пропущено_причины` (напр. `разрыв_seq:2 не_tls:1`), только когда
пропуски есть. Поведение сборки при этом НЕ изменилось — это чистая
наблюдаемость. Тесты: `TestGiveUpReasonIsReported` (каждый путь ставит свою
причину), `TestGiveUpReasonStrings` (метки непусты и различимы).

**Фикс остатка `не_tls` (фрагментированное рукопожатие).** Полевая разбивка
показала, что все оставшиеся 3 пропуска — `не_tls` (а НЕ переупорядочение, как
можно было предположить; буфер reorder не понадобился). Корень: детектор
`TLSHelloDetector` (`internal/intercept/tls.go`) считал «TLS, ждём ещё» только
`ErrIncomplete`, а крупный ClientHello Chrome (post-quantum key_share) шлётся
рукопожатием на НЕСКОЛЬКО TLS-записей — строгий разбор отдаёт
`ErrFragmentedHandshake`. Эта ошибка падала в `default` → `isTLS=false` →
сборка сдавалась → настоящий SNI уходил сырьём → TSPU рвал CDN-загрузку.
Правка: `ErrFragmentedHandshake` обрабатывается наравне с `ErrIncomplete` —
пробуем нестрогий разбор, а он находит `server_name` в первой записи (имя
лежит в начале расширений) и делает десинк применимым. Собирать всё
многозаписевое сообщение не нужно. Тест
`TestDetectorFragmentedHandshakeAppliesViaSNI`: двухзаписевой ClientHello
(строгий разбор даёт `ErrFragmentedHandshake`) теперь распознаётся применимым,
SNI и точки разреза извлекаются. `go test -race ./...` зелёный.

## Волна «Примитивы md5sig и IPv6 Hop-by-Hop» — ноябрь 2026 (ветка `feat/wave1-md5sig-ipv6ext`)

Закрыты пункты 4 (`md5sig`) и 5 (IPv6 extension headers) Волны 1
(`docs/ARCHITECTURE.md`): расширение арсенала фейков на случай, если TSPU
начнёт распознавать текущий cover-паттерн `tcp_overlap`.

**md5sig** — новый вид `ActionMD5Sig` (токен `md5sig`), возможность
`CapMD5Sig` (только packetexec). Арность 1 (как Tamper): помечает кусок
фейком, в который исполнитель вставляет опцию TCP MD5 Signature (RFC 2385,
вид 19, 18 байт) с заведомо неверной подписью, и спускается в ветвь. Обычно
под Duplicate (decoy рядом с настоящими данными). Многие DPI MD5 не
проверяют и впитывают фейк; хост на соединении без MD5 обязан сегмент
отбросить. Вставка опции расширяет заголовок TCP (двигает смещение данных),
поэтому вынесена отдельным видом, а не режимом Tamper.

**IPv6 Hop-by-Hop** — новый вид `ActionIPv6Ext` (токен `ipv6_ext`),
возможность `CapIPv6ExtHeader` (только packetexec). Арность 1: помечает
фейк, в который вставляется минимальный (8 байт, PadN) заголовок расширения
IPv6 Hop-by-Hop перед протоколом верхнего уровня. Рассинхрон разбора:
упрощённый DPI может не дойти за цепочкой расширений до TCP/SNI. Действует
ТОЛЬКО на IPv6; на IPv4 приём неисполним — исполнитель возвращает ошибку
недоступности, движок пропускает оригинал сырьём (тот же класс, что правка
IPv6-поля на IPv4).

Общее: вставка байт в заголовок (в отличие от правок Tamper на месте)
живёт в `internal/packet` (`InsertTCPOption` + `MD5SignatureOption`,
`InsertIPv6HopByHop`) — строит новый буфер, двигает смещения, обновляет
длины; суммы пересчитывает вызывающий после всех правок. В `desync.Op`
добавлены флаги `InsertMD5Sig` и `InsertIPv6HopByHop`; packetexec вставляет
заголовок ДО пересчёта сумм. Генератор новых видов не порождает (switch в
`allowedInternalKinds` их не включает, как и `tcp_overlap`), поиск не
затронут.

Тесты на реальных байтах: `internal/packet` (вставка опции TCP/MD5 на IPv4
и IPv6, Hop-by-Hop, превышение предела смещения данных, отказ на не-TCP и
на IPv4), `internal/desync` (план под Duplicate и стек с Tamper),
`internal/packetexec` (фейк с опцией MD5 и верными суммами; `ipv6_ext` на
IPv4 — ошибка и ноль отправленного), `internal/strategy` (JSON round-trip,
`CapMD5Sig`/`CapIPv6ExtHeader`, отказ на параметрах и на отсутствии ветви).

Примеры: `examples/strategies/md5sig-fake.json`,
`examples/strategies/ipv6-hopbyhop-fake.json` (+ строки в README с ручной
инструкцией). Скрипт прогона: `scripts/test-all.bat` (build + vet +
подробные тесты примитивов + полный `-race`).

Проверка: `go build`/`go vet` чисто, `go test -race -count=1 ./...` — все
пакеты зелёные. Поведение `main` не меняется: новые виды работают только
при явном указании в стратегии.

## Волна «GUI на многосегментных CDN ClientHello + разбор затупа голоса» — ноябрь 2026 (PR #32)

**Симптом 1 (GUI).** Иконки, эмодзи, аватарки, Rive-анимации с
`cdn.discordapp.com` то грузились, то нет (`net_error -101`, «Failed to
fetch»). В журнале движка (`state/events.jsonl`) — чёткая закономерность:

```
cdn.discordapp.com assembled:true  → strategy.failed (exec_failed)
cdn.discordapp.com assembled:false → strategy.applied
```

**Корень.** Крупный ClientHello Chrome шлёт несколькими TCP-сегментами. На
сборке (`applyAssembled`) движок досылал сегменты до начала SNI сырьём, а
десинковал только ХВОСТ от начала имени. Но `tcp_overlap` перекрывает
нагрузку cover-пакетом в 681 байт: если хвост короче 681 (а на
многосегментном hello он почти всегда короче), перекрытие невозможно →
`exec_failed` → настоящий ClientHello с открытым SNI уходит сырьём → TSPU
рубит → ресурс GUI не грузится. Одиночные (однопакетные) hello работали —
отсюда «мигание».

**Правка.** В `internal/intercept/engine.go`, `applyAssembled`: для
стратегий, требующих `CapTCPOverlap` (перекрывают весь ClientHello),
десинкуем ВЕСЬ собранный hello одним куском (как одиночный), а не хвост.
Длина L = полный hello (у Chrome >681), cover перекрывает его хвост, SNI
скрыт. Стратегии `fragment`/`split` идут прежним путём (хвост) — ветка
срабатывает только по `CapTCPOverlap`, голос не затронут.

Тест `TestAssembledTCPOverlapDesyncsWholeHello`: реальный двухсегментный
ClientHello (имя во втором сегменте, полный hello >681, хвост <681) — движок
шлёт ровно cover(681)+реальный hello с верными seq и суммами, а не падает в
сырьё.

**Симптом 2 (голос «затуп на AUTHENTICATING по минуте»).** Разобран в ту же
сессию. Итог — root cause НЕ в стратегии и НЕ в номере порта, а в
накопленной памяти движка:

- `state/rtctrack.json` — память о «плохих» (SNI,порт) RTC-серверах, из неё
  строится blocklist, который их обходит. Файл копится по мере
  использования и переживает перезапуски (`AutoSaver` + восстановление на
  старте). Пока он «прогрет», залипающие сервера обходятся → голос заходит
  мгновенно; на холодном старте каждый плохой сервер пробуется заново и
  виснет. **Удалять `state/rtctrack.json` нельзя** — это стирает выученное и
  возвращает затупы, пока память не нарастёт снова.
- Рычаг на стороне пользователя, когда флачит конкретный регион серверов:
  Override Region в настройках голосового канала (напр. Finland вместо
  Stockholm — все `c-arn*` это Стокгольм).

**Отрицательные результаты (отвергнуты, чтобы не повторять):**

- `--rtc-redirect` в лаунчере (PR #29) — переклейка душимых RTC-портов на
  8443 даёт `4006 Session is no longer valid` на КАЖДОМ подключении: Discord
  привязывает голосовую сессию к серверу/порту, на другом порту тот же
  сервер её не признаёт. Откат — PR #30. `rtcredirect` оставлен в движке для
  экспериментов, но лаунчер его не передаёт (подтверждено в
  `docs/discord-ru.md`).
- Firewall-блок порта 2096 (`netsh ... movok-discord-bad-rtc`) — не помог:
  затуп не привязан к номеру порта (одно из 2096-подключений заходило за
  573 мс, а блок не убрал затупы на других).
- `discord_voice` только split, без badseq-фейка (PR #31, закрыт без мержа)
  — убрал затуп на части серверов, но сломал рукопожатие на других (badseq
  нужен части серверов). Голосовую стратегию `badseq+apple+split` в

**Проверка.** `go build`/`go vet` чисто, `go test -race -count=1 ./...` —

## Волна «ультимативная структура: все пять волн» — ноябрь 2026

Инварианты «как часы» (безопасность после краха, один экземпляр, панико-
стойкость, наблюдаемость) + расширенный арсенал приёмов обхода.

**Волна 0 — инварианты «как часы»** (`internal/safego`, `internal/sysmanifest`,
`internal/enginelock`, `cmd/evasion/cleanup`):

- `safego.Group` — набор горутин с общим Wait и обязательным `recover()`:
  паника в фоне теперь не роняет процесс, перехват переходит в прозрачный
  режим, оператор видит стек в журнале. 7 тестов.
- `sysmanifest` — журнал системных изменений (firewall rule, hosts entry)
  с атомарной записью (tmp + rename), чтобы отмена могла воспроизвестись из
  любого состояния процесса, включая отсутствующий процесс. 13 тестов.
- `enginelock` — mutex-файл `state/engine.lock` с массивом записей
  `{pid, filter, started_at}`, OS-ветка проверки живости PID. Второй запуск
  на том же фильтре получает ErrConflict с внятным сообщением. 12 тестов.
- `evasion cleanup` — читает манифест, откатывает каждое изменение (netsh
  advfirewall firewall delete rule / hosts.Remove). Флаги: --json, --dry-run,
  --force. 4 теста.
- Единственный `panic(...)` в `internal/store/writer.go:96` заменён на
  возврат ошибки; NewWriter теперь `(*Writer, error)`.
- Фоновые горутины в `runInterceptAuto` (sandbox-engine, sandbox-probes,
  background-search) завёрнуты в `safego.Group` с onPanic, поднимающим
  прозрачный режим обоих контуров.
- Все `evasion hosts apply` теперь регистрируют изменение в sysmanifest.

**Волна 1 — расширение арсенала примитивов**:

- `internal/quicfake` — benign-QUIC v1 Initial long-header 74 байт
  (`BenignInitial74()`) для подстановки в UDP decoy голоса. DPI
  классифицирует UDP-поток как QUIC к постороннему хосту, вместо
  «голос Discord». `--voice ttl-quic` / `--voice badsum-quic` — новые
  режимы. 9 тестов quicfake + 4 теста интеграции.
- TLS record-layer split (`FragProto = FragTLSRecord`) — разрез
  ClientHello не на уровне TCP, а на уровне TLS: обе половины остаются
  валидными TLS-записями, сервер склеивает, DPI часто парсит только
  первую запись и теряет SNI если он во второй. 6 тестов desync.

**Волна 2 — реестр готовых нагрузок (6 ClientHello в tlsfake)**:

- `BuildClientHello(sniHost)` — обобщённый конструктор; шесть кэшированных
  пресетов: Google / Cloudflare / Apple / Microsoft / Yandex / VK.
- Реестр `strategy.FakePresetNames()` для детерминированного перебора
  (нужно генератору). 5 тестов tlsfake.

Зачем много: один статичный пресет сам становится маркером обхода на
продвинутом DPI; разные пресеты размывают сигнатуру и выглядят как разные
браузеры разных пользователей. Плюс: часть провайдеров агрессивнее душит
именно google-SNI, часть — зарубежные SNI (российские vk/yandex обходят
классификацию «иностранный трафик»).

**Волна 3 — поток событий** (`internal/events`):

- `Event {At, Kind, FlowID, Attrs}` → JSON Lines в `state/events.jsonl` с
  ротацией. 11 видов события покрывают жизненный цикл соединения.
- `Writer.Open/Enqueue/Close` — асинхронный приёмник, не блокирует горячий
  путь, при переполнении отбрасывает со счётчиком Dropped.
- 5 тестов events: enqueue+readback, drops at closed, overflow, FlowID
  hex, rotation.

Интеграция с движком (OnFlowStarted/OnClientHelloSeen хуки) — следующая
итерация.

**Волна 4 — RTC-tracker** (`internal/rtctrack`):

- `Tracker` — агрегатор статистики пар `(SNI, port)` для Discord-голоса:
  `Observe/Settled/Reset/Elapsed` входы, `AvgDwell/SuccessRate/LivenessScore`
  метрики, `Rank(k, minObserved)` — лучшие k пар по эвристическому
  индексу живучести. `Prune(olderThan)` для очистки устаревшего.
- 9 тестов: все метрики, параллельный доступ под -race, Snapshot копия.

Готово к интеграции в cmd/evasion/intercept.go в следующей итерации
(триггеры по событиям перехвата).

Итог волны: 5 новых пакетов (`safego`, `sysmanifest`, `enginelock`,
`quicfake`, `events`, `rtctrack`), 1 новая команда CLI (`evasion cleanup`),
новый FragProto (TLSRecord), 6 новых presets, 2 новых режима `--voice`,
~70 новых тестов, +3700 строк кода, 0 panic в проде. go test -race ./... —
зелёный на всех 41 пакете.

## Волна «откат CDN стратегии к работающему состоянию» — ноябрь 2026 (PR #11)

PR #10 заменил работающую CDN-стратегию `tcp_checksum corrupt + cloudflare
preset + split` на голосовую `tcp_seq add -10000 + apple preset + split` —
исходя из гипотезы что голосовая связка сильнее. На практике получилось
**хуже**: `повторов_clienthello` вырос с 48 (на 145 CDN-попыток в PR #9) до
**104** (на 165 попыток в PR #10) — удвоение.

Пользователь прямо подтвердил: картинки загружались **до** PR #10, перестали
**после**. Регрессия.

Корень: `tcp_seq add -10000` работает против Cloudflare Spectrum (TCP-прокси
голосовых серверов — почти не делает state tracking, принимает всё в разумном
окне), но **ломает обычный HTTPS** на Cloudflare CDN / Fastly CDN, где TCP
state tracker строго проверяет seq в окне. Фейковый пакет с seq-10000 клиент
не считает отправленным, а сервер потом видит ClientHello с «правильным» seq
за границей RTO-окна — рукопожатие срывается.

Откат: `discord_cdn` возвращена на `tcp_checksum corrupt + tls_clienthello_
cloudflare + split` (как в PR #9). Расширенный rtctrack-фильтр из PR #10
оставлен — он не затрагивает поведение движка, только даёт диагностику per-SNI
по всему Discord-радиусу.

- `examples/config.json` — `discord_cdn` вернулся на корректную связку.
- 41 пакет `go test -race -count=1 ./...` зелёный.

Урок: голосовая стратегия ≠ CDN-стратегия, даже если оба идут через
Cloudflare. Шов между Spectrum и обычным HTTPS CDN проходит по тому,
насколько строго TCP state tracker в сервере принимает пакеты вне окна.
Не выравнивать стратегии между группами без боевой проверки на каждой.

## Волна «TLS-record split для cdn.discordapp.com» — ноябрь 2026 (PR #13)

Пользователь жалуется: гифки на `media.discordapp.net` грузятся, фотки на
`cdn.discordapp.com` — нет. Оба домена шли в одной группе `discord_cdn` с
одной стратегией `tcp_checksum corrupt + cloudflare preset + TCP split`.
Значит TSPU режет эти два домена по-разному: разделение групп позволит
нам применить разные стратегии.

Разделение:
- `discord_cdn_media` → `discordapp.net` (гифки, превью) → **оставляем
  рабочую стратегию** (corrupt-checksum + cloudflare + TCP split)
- `discord_cdn_images` → `cdn.discordapp.com` (оригиналы фоток) →
  **новая стратегия: TLS-record split** (fragment proto=tls_record,
  at=inside_sni, order=forward)

Почему TLS-record split:
- Не трогает TCP state (нет badseq, нет corrupt checksum)
- Не создаёт фейковых пакетов (не триггерит TSPU anti-DDoS)
- Делит ClientHello на две валидные TLS записи с общим handshake-семантикой
- Сервер склеивает автоматически (TLS спеka гарантирует)
- DPI с простой regex не ждёт разделения SNI между TLS records и может
  пропустить блокировку

Это проверенный приём zapret'а/byedpi против простейших DPI. Если TSPU
обходится так — фотки грузятся. Если нет — пойдём пробовать другие
комбинации (fake-badsum с nonstandard preset, или IP-fallback на известный
Cloudflare IP).

- `examples/config.json`:
  - Разделил `discord_cdn` на `discord_cdn_images` + `discord_cdn_media`
  - `discord_cdn_images` → новая стратегия с `tls_record` фрагментацией
  - `discord_cdn_media` → оставил старую стратегию без изменений

## Волна «multi-IP transport_fallback» — ноябрь 2026 (PR #16)

PR #15 добавил `cdn.discordapp.com` в hosts с единым `safe_ip=162.159.138.232`
(тем же что для gateway). GUI отрисовался, но фотки по-прежнему не грузятся.
Пользователь подтвердил: `type hosts | findstr discord` показывает все три
строки, но контент не идёт.

Корень: Cloudflare Spectrum — IP-пулы по сервисам:
- `.232` суффикс (`162.159.*.232`) — media.discordapp.net
- `.233` суффикс (`162.159.*.233`) — cdn.discordapp.com
- `.234` суффикс (`162.159.*.234`) — gateway.discord.gg

`162.159.138.232` обслуживает SNI gateway + media (работает), но **не
обслуживает SNI cdn.discordapp.com** — тот Cloudflare Spectrum endpoint
отвечает только для своего набора SNI, иначе отбивает соединение.

Решение: разные `safe_ip` для разных доменов. Расширил `TransportFallback`:
- `TransportFallback.Entries []TransportFallbackEntry` (новое поле)
- Каждая Entry = `{SafeIP, Domains}` (свой IP для своих доменов)
- Старая форма `safe_ip + domains` сохранена, при парсинге сворачивается
  в одну Entry — обратная совместимость

Новый формат в `examples/config.json`:
```json
"transport_fallback": {
  "enabled": true,
  "entries": [
    {
      "safe_ip": "162.159.138.232",
      "domains": ["gateway.discord.gg", "media.discordapp.net"]
    },
    {
      "safe_ip": "162.159.130.233",
      "domains": ["cdn.discordapp.com"]
    }
  ]
}
```

Валидация: если `enabled=true` — должен быть непустой `entries` (или легаси
`safe_ip+domains`, которые свернутся в одну Entry). Нельзя задать и то и то
одновременно (неоднозначно). Каждая Entry — валидный IP и непустой список
доменов.

Внутри applyFallback все Entries собираются в один управляемый блок (единый
ID `cloudflare-fallback`), просто разные записи получают разные IP. Hosts
рендерится корректно:

```
# >>> evasion:cloudflare-fallback begin >>>
162.159.138.232 gateway.discord.gg
162.159.138.232 media.discordapp.net
162.159.130.233 cdn.discordapp.com
# <<< evasion:cloudflare-fallback end <<<
```

- `internal/config/config.go` — расширил TransportFallback + validate
- `cmd/evasion/hosts.go` — applyFallback итерирует по Entries,
  логирование через `transportFallbackDomains(f)` helper
- `examples/config.json` — переведён на новый формат с CDN на отдельном IP
- 41 пакет `go test -race -count=1 ./...` зелёный

Ожидание: `cdn.discordapp.com` теперь идёт на свой IP `162.159.130.233`
(реальный DNS-пул). Если этот Cloudflare endpoint обслуживает CDN SNI
— фотки грузятся.

## Волна «TCP overlap primitive для обхода SNI-блокировки» — ноябрь 2026 (PR #23/#24)

Диагностический скрипт PR #22 показал: все 5 Cloudflare IP для
`cdn.discordapp.com` отвергают TLS-рукопожатие с этим SNI с таймаутом
10 сек на любом из IP. TCP connect проходит, но ClientHello с этим SNI
дропается независимо от маршрута. Это SNI-блокировка на уровне TLS, и
никакая обфускация TCP-заголовка, hosts-подмена или fake-pre-клиент
без контроля TCP sequence не помогают: имя остаётся в reassemble'нной
склейке. Нужен был новый примитив.

**Как работает `tcp_overlap`**:

Движок удерживает оригинальный ClientHello (seq=SN, size=L) и шлёт
ДВА пакета:

1. **Cover-пакет** (M байт, M < L): заранее подготовленный безобидный
   ClientHello фиксированного размера. Отправляется с TCP seq = SN +
   L - M, то есть **перекрывает по TCP sequence number последние M
   байт** настоящей нагрузки.

2. **Настоящая нагрузка** (L байт) уходит ВТОРЫМ пакетом с seq = SN,
   полностью покрывая диапазон [SN..SN+L].

Сервер (RFC 1122 TCP overlap): байты [SN..SN+L-M] приходят из пакета
(2) без перекрытия; байты [SN+L-M..SN+L] перекрыты обоими пакетами;
получатель применяет правило «последний пришедший перезаписывает» —
пакет (2) пришёл после (1), его байты побеждают. Сервер получает
оригинальный ClientHello целиком, рукопожатие проходит.

DPI (без знания TCP state): видит в первом пришедшем пакете валидный
cover-ClientHello, классифицирует соединение по его SNI, пропускает.
Второй пакет уже не парсит — классификация по соединению сделана.
Настоящий SNI (например `cdn.discordapp.com`) остаётся невидимым.

**Реализация**:

- `internal/core/action.go`: новый `ActionTCPOverlap` — лист с
  параметром `preset`. Арность 0 (детей нет).
- `internal/core/capability.go`: новая `CapTCPOverlap`. Только у
  packetexec: в прокси ОС назначает seq сама по порядку записи,
  перекрытие не задать.
- `internal/strategy/params.go`: `TCPOverlapParams { Preset string }`.
  Валидация: `Preset` непуст и зарегистрирован в реестре. Требует
  `CapTCPOverlap` в `requiredCapabilities`.
- `internal/strategy/registry.go`: регистрация `ActionTCPOverlap` в
  реестре видов и в `Kinds()` (генератор сам подхватит).
- `internal/tlsfake/cover681.go`: встроенный через `go:embed`
  681-байтный cover-ClientHello (валидная форма протокола с
  общеупотребительным набором расширений). Размер зафиксирован — на
  нём завязан расчёт overlap-смещения.
- `internal/tlsfake/cover681_test.go`: три теста (фиксированный размер
  681, TLS handshake content type 0x16, возвращаемая копия).
